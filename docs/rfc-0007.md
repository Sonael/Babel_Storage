# RFC 0007: Verificação por Árvore Merkle (BSP v6)

**Status**: Implementado
**Versão**: BSP v6
**Data**: 2026-07-24
**Autor**: Sonael de Albuquerque Angelos Neto.

## Resumo

O BSP v6 adiciona a raiz de uma árvore Merkle binária SHA-256, construída sobre
os hashes por chunk, aos metadados. Essa raiz de 32 bytes — protegida pela
assinatura RSA quando os metadados são assinados (BSP v4) — permite **provar que
um chunk específico é autêntico recuperando apenas aquele chunk**, sem baixar o
arquivo inteiro.

Esta RFC formaliza a proposta descrita na [RFC 0006](rfc-0006.md) Seção 1.1.

## 1. Motivação

**Problema**: Verificar a integridade de um arquivo exigia baixar todos os
chunks e recalcular o hash completo (BSP v1). Para um arquivo de 350 chunks,
confirmar que um único chunk não foi adulterado custava centenas de requisições
à Biblioteca de Babel.

**Solução**: Selar a lista de hashes por chunk sob uma única raiz Merkle. Um
verificador pode então:

*   Recompor a raiz offline a partir dos hashes armazenados e compará-la com a
    raiz registrada (detecta adulteração da lista de hashes).
*   Recuperar **um** chunk, calcular seu hash e verificar uma **prova de
    inclusão** curta (log₂N hashes irmãos) contra a raiz.

### 1.1 Limitação importante

A árvore Merkle habilita **verificação de integridade parcial**, mas **não**
habilita download seletivo com descompressão isolada. O Zstandard (RFC 0002)
mantém estado entre blocos: para descomprimir o chunk N é necessário ter
processado os chunks 0..N-1. Portanto, `verify-chunk` prova autenticidade, mas
a restauração do conteúdo continua exigindo todos os chunks.

## 2. Especificação da Árvore

### 2.1 Construção

*   **Folhas**: os digests SHA-256 brutos (32 bytes) de cada chunk, na ordem dos
    chunks. São exatamente os hashes por chunk já registrados nos metadados
    (BSP v2), então a árvore inteira pode ser reconstruída offline.
*   **Nós internos**: `sha256(esquerda ‖ direita)`.
*   **Nível ímpar**: quando um nível tem número ímpar de nós, o último nó é
    pareado consigo mesmo (duplicado).
*   **Raiz**: o único nó do nível mais alto. Para um arquivo de um único chunk, a
    raiz é igual ao hash daquele chunk e a altura é 0.

```python
def compute_root(leaves: List[bytes]) -> bytes:
    while len(leaves) > 1:
        parents = []
        for i in range(0, len(leaves), 2):
            left = leaves[i]
            right = leaves[i + 1] if i + 1 < len(leaves) else left
            parents.append(sha256(left + right).digest())
        leaves = parents
    return leaves[0]
```

### 2.2 Prova de Inclusão

A prova para a folha no índice `i` é a lista ordenada de digests irmãos, de baixo
para cima, cada um marcado com o lado (esquerda/direita). O verificador dobra a
folha com os irmãos e compara o resultado com a raiz:

```python
def verify_proof(leaf, proof, root) -> bool:
    h = leaf
    for sibling, sibling_is_left in proof:
        h = sha256(sibling + h) if sibling_is_left else sha256(h + sibling)
    return h == root
```

O comprimento da prova é ⌈log₂N⌉ — 6 hashes para 34 chunks, 9 para 350.

## 3. Alterações nos Metadados

Dois campos compactos são adicionados ao dicionário serializado, **apenas quando
presentes**:

| Chave | Campo | Descrição |
|-------|-------|-----------|
| `mr` | `merkle_root` | Raiz Merkle em hexadecimal (64 caracteres) |
| `mh` | `merkle_height` | Altura da árvore (inteiro, 0 para 1 chunk) |

```json
{
  "f": "large_file.dat",
  "h": "file_sha256...",
  "c": 34,
  "v": "v6",
  "mr": "78eae4c1cd9dd7ae...",
  "mh": 6,
  "chk": [...]
}
```

### 3.1 Compatibilidade retroativa

*   Metadados BSP v5 (sem `mr`/`mh`) carregam normalmente; `merkle_root` fica
    vazio e as operações de v6 são simplesmente puladas.
*   Como os campos Merkle só entram no dicionário quando presentes, **assinaturas
    BSP v5 antigas continuam válidas** — o dicionário assinado não muda.
*   Em metadados v6, a raiz é calculada **antes** da assinatura, então a
    assinatura passa a proteger também a raiz.

## 4. Comportamento na Verificação

### 4.1 Verificação Offline (`verify-metadata`)

Adiciona uma sexta checagem à [RFC 0005](rfc-0005.md) Seção 3.1: recompor a raiz
a partir dos hashes armazenados e compará-la com `merkle_root`.

*   **Raiz confere** → aprovado.
*   **Raiz não confere** → a lista de hashes foi alterada (falha fatal).
*   **Sem raiz (pré-v6)** → aviso não fatal; só reprova em modo estrito.

### 4.2 Verificação de Chunk Único (`verify-chunk`)

```bash
python babel_storage.py verify-chunk arquivo.json.gz \
  --index 17 \
  --pubkey public.pem
```

1.  (Opcional) Verifica a assinatura RSA da metadata.
2.  Recupera **somente** o chunk no índice indicado da Biblioteca de Babel.
3.  Decodifica, calcula o SHA-256 do chunk recuperado.
4.  Monta a prova de inclusão a partir dos hashes irmãos na metadata.
5.  Verifica a prova contra `merkle_root`.

Se o chunk recuperado foi adulterado, seu hash difere e a prova não reconstrói a
raiz assinada → detectado. Sai com código 1 em caso de falha.

### 4.3 No Download

Antes de recuperar qualquer chunk, o download recompõe a raiz a partir dos hashes
da metadata e a compara com `merkle_root`. Em modo estrito, uma divergência
aborta imediatamente — barato, offline, antes de gastar minutos na rede.

## 5. Interface Web

Todas as operações têm paridade na interface web:

| Ação na web | Equivalente na CLI |
|-------------|--------------------|
| A raiz Merkle aparece no modal **Info** | `info` |
| A checagem "Merkle root" aparece no modal **Verify** | `verify-metadata` |
| O escudo por chunk no modal **Info** | `verify-chunk --index N` |

## 6. Considerações de Segurança

*   A raiz Merkle só é confiável na medida em que a metadata é confiável. Sem
    assinatura (BSP v4), um atacante poderia reescrever hashes **e** a raiz.
    `verify-chunk` é significativo sobretudo com uma raiz assinada.
*   A construção não faz separação de domínio entre folhas e nós internos. Como
    todas as folhas têm comprimento fixo de 32 bytes e o número de folhas é fixado
    por `chunk_count` (protegido pela assinatura), ataques de segunda pré-imagem
    por reinterpretação da árvore não se aplicam neste modelo de ameaça.

## 7. Impacto no Desempenho

| Operação | Custo |
|----------|-------|
| Construir a raiz no upload | O(N) hashes, desprezível |
| Verificação offline da raiz | O(N) hashes, ~ms |
| `verify-chunk` | 1 requisição de rede + ⌈log₂N⌉ hashes |
| Overhead de armazenamento | +~80 bytes por metadata (raiz + altura) |
